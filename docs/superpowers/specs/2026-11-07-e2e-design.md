# End-to-end tests: design

Date: 2026-11-07. Status: approved in conversation, ready for a plan.

## Why

Today the app is covered piece by piece (domain, reducer, components under jsdom, the Electron modules) and by two smoke checks (`electron:smoke` imports a save without a window; `electron:smoke-ui` reaches the welcome screen). Nothing drives the real app the way a person does: open it, load a save, drag players, edit, close, reopen. The Windows installer has never run at all. The owner has no Windows machine, so the test must run on GitHub's Windows runner and report back.

Success: a green run on `windows-latest` means the installer installs, the installed app opens, a person can complete the whole planning flow, their data survives closing and uninstalling, and a corrupt data file is handled without losing anything.

## Goals

- Drive the real Electron app (real window, real preload, real CSP, real importer child process) with Playwright.
- Run the same scenarios on Linux (local, CI optional) and on Windows (CI).
- Include pointer drags (pitch tokens, table rows), which have never been exercised by hand or by test.
- Cover the Windows-only path: silent install, launch the installed app, uninstall, data folder kept.
- Run the full flow against the owner's real save locally, skipped automatically when no save is present.

## Non-goals

- No backdoors in shipped code: no test-only environment variables or flags in `src/`. The e2e uses the app's existing behaviour plus what Playwright can do from outside.
- No real `.fm` save in CI, and no synthetic `.fm` writer. A save is private and the format is not reproducible by us.
- No visual regression or screenshot comparison.
- No publishing, no secrets, no code signing.
- Not a replacement for the unit and component tests.

## Constraints

- Public, open-source repo: fixtures are invented players only (no real people, no save content).
- Playwright is a devDependency only; it never ships in the installer. Playwright browsers are not downloaded (Electron is used).
- The e2e job must stay under roughly 15 minutes on the Windows runner.

## How it works

**Launching.** Playwright's `_electron.launch` starts the built app with `--user-data-dir=<fresh temp dir>` (Electron honours it, so each scenario gets an isolated data folder and the real `%APPDATA%` is never touched). The native "open file" dialog is replaced from outside with `electronApp.evaluate` (stub `dialog.showOpenDialog` to return a chosen path).

**Fake importer without touching product code.** Level A uses an *e2e build* of the app: same code, built to a separate folder, where only `importer.cjs` is replaced by a small scripted importer that emits progress and writes a valid, invented snapshot (built with the snapshot contract in `src/shared/snapshot.ts`, so it fails if the contract drifts). The scripted importer can also be told, through the chosen "save" file's contents, to produce a second squad (one player gone, one new) or to hang so the scenario can cancel. The "save" is a tiny text file the fake reads; it is not a real save.

**Installed-app check (Windows only).** The real installer is run silently (`/S`), the installed executable is launched with a pre-seeded data folder (a `snapshot.json` and `owner.json` written by the test, since the installed importer is the real one and has no save to read), the squad shows, then the app is uninstalled and the data folder is checked to still exist.

**Level B (local only).** The real build, the real importer, the owner's save from `saves/*.fm` or `FM_SAVE`; skipped when absent. Checks the known counts for the sample save (31 first team, 5 reserves, 33 Sub-18) and that the plan survives close and reopen.

## Scenarios

Level A (fake importer; Linux and Windows):
1. First launch shows the welcome screen; loading a save shows progress, then the invented squad.
2. Drag a player onto a pitch slot; drag a table row; change formation; change currency in Ajustes.
3. Edit, close the window immediately, reopen: the edit is there.
4. Start an import, cancel it mid-way: the previous squad and plans are unchanged.
5. Import a second, different squad: plans remain, the player who left is flagged "ya no está en la plantilla", the new player appears unassigned.
6. Corrupt `owner.json` before launch: the app explains it and writes nothing; the file is byte-identical afterwards.

Installer (Windows only, in CI):
7. Silent install, launch installed app with seeded data, squad shows, uninstall, data folder remains.

Level B (local, real save): the full flow of 1 to 3 with the real save and the known counts.

## Decisions I took (the owner did not specify)

- Playwright's Electron support rather than a custom harness.
- A separate e2e build with a swapped importer, instead of an environment variable in the app.
- `npm run e2e` for Level A and `npm run e2e:real` for Level B.
- A new step in `.github/workflows/windows.yml` after `npm run dist`, in the same job, so it runs against the artifact just built.
- Scenarios are written against roles, labels and visible Spanish text, not CSS classes. Where the planner has no stable handle for a drag target, a stable `aria-label` is added to the component (this is a UI change and gets a component test).
- If pointer drags prove unreliable on the CI runner, that scenario is marked `fixme` with the reason written in the test and in `docs/09-distribution.md`, rather than weakened until it passes.

## Left to the builder

File layout under `tests/e2e/`, the scripted importer's mode protocol, the synthetic squad's size and names, timeouts, and how the Windows job passes the installer path to the test.

## Risks

- First run of the installer on Windows may fail for reasons unrelated to the tests (builder config, SmartScreen is not involved in silent installs). Expect one or two rounds of fixing from CI logs; the owner triggers the run and shares the log.
- Pointer-event drags under Playwright can need manual `mouse.move` steps; the components use `onPointerDown` plus document-level move handlers.
